# Feature Specification: 入口頁與老師頁面對齊 OpenSpec 組

**Feature Branch**: `003-align-entry-pages`

**Created**: 2026-11-27

**Status**: Draft

**Input**: OpenSpec 組的交接文件〈入口頁與老師頁面對齊 OpenSpec 組（給 SpecKit 組）〉（2026-11-27），原文見
[handoff-from-openspec.md](./handoff-from-openspec.md)。摘要："兩組進入系統的方式不同。經兩組討論，決定由 SpecKit 組完全對齊 OpenSpec 組的做法：
首頁 `/` 改為學生的「加入組別」頁，並提供「我是老師」按鈕；老師的所有功能合併到 `/teacher` 單一頁面；舊網址導向新網址。
這次只改前端頁面與頁面網址，伺服器的功能、判定、權限與資料都不變。"

**Depends on**: [001 學習單匯入](../001-guided-notes-import/spec.md)、[002 線上分組搶答活動](../002-online-buzz-activity/spec.md)（兩者皆已完成）。
本功能只重新安排既有功能在畫面上的位置與進入方式，不新增或改變任何業務規則。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 學生從首頁加入組別並作答 (Priority: P1)

學生在同一台電腦開啟新的瀏覽器視窗，進入系統首頁，就直接看到「加入組別」。輸入老師發的組別代碼並按「加入」後，
同一頁立即切換成該組的作答畫面，網址不變；學生不需要知道或輸入任何其他網址。

**Why this priority**: 學生人數最多、最常進入系統。目前學生必須自己把網址改成另一個頁面，課堂上容易出錯；
這也是兩組在操作上最明顯的差異。

**Independent Test**: 只完成學生頁也能單獨驗證：開啟首頁、輸入代碼加入，並完成作答、看到結果，不需要用到新的老師頁
（老師端可暫時沿用既有方式建立與開始活動）。

**Acceptance Scenarios**:

1. **Given** 任何人開啟首頁，**When** 頁面載入，**Then** 看到「加入組別」標題、一段說明（每個瀏覽器視窗各自保有自己的身分，
   可以在不同視窗分別開啟老師與各組畫面）、組別代碼欄位，以及並排的「加入」「我是老師」兩個按鈕；畫面上沒有老師密碼欄。（E-01）
2. **Given** 一場準備中的活動與第一組的正確代碼，**When** 學生在首頁輸入代碼並按「加入」，**Then** 同一頁顯示第一組的作答畫面
   （組名、目前階段、冷卻、作答區，結束後顯示結果與各組成功題數），網址仍是首頁，「加入組別」區塊與「我是老師」按鈕都隱藏。（E-02）
3. **Given** 學生輸入錯誤或格式不正確的代碼，**When** 按「加入」，**Then** 留在「加入組別」，並顯示既有的錯誤訊息，不透露任何組別資訊。
4. **Given** 一個已加入第一組的學生視窗，**When** 重新整理頁面，**Then** 直接回到第一組的作答畫面，不需要重新輸入代碼。
5. **Given** 一個已加入的學生視窗，**When** 老師重新產生該組代碼，或伺服器重啟導致活動已中斷，**Then** 該視窗回到「加入組別」，
   並顯示既有的提示訊息（例如「活動已中斷，請老師重新建立。」）。（E-09）

### User Story 2 - 老師從首頁進入老師頁並登入 (Priority: P1)

老師開啟首頁後按「我是老師」，進入老師頁 `/teacher`。未登入時只看到「老師登入」；輸入密碼登入後，所有老師功能都在同一頁，
網址不變。登出後回到同一頁的登入畫面。

**Why this priority**: 首頁改成學生頁之後，老師必須有清楚的入口，否則無法使用系統。

**Independent Test**: 從首頁按「我是老師」，登入、重新整理、登出，確認每一步的畫面與網址都正確。

**Acceptance Scenarios**:

1. **Given** 在首頁，**When** 按「我是老師」，**Then** 網址變成 `/teacher`，並顯示「老師登入」（密碼欄與「登入」按鈕）。（E-03）
2. **Given** 在 `/teacher` 的登入畫面，**When** 輸入正確密碼並登入，**Then** 同一頁由上而下依序顯示：匯入學習單、已確認的學習單、
   建立搶答活動、目前活動、活動清單；網址仍是 `/teacher`；頁首只有「登出」，畫面上沒有切換到其他網頁的連結。（E-04）
3. **Given** 輸入錯誤密碼或連續錯誤達上限，**When** 按「登入」，**Then** 留在登入畫面，並顯示既有的錯誤或鎖定訊息。
4. **Given** 已登入的老師視窗，**When** 重新整理頁面，**Then** 直接顯示登入後的畫面；若登入已失效，則顯示登入畫面。
5. **Given** 已登入的老師視窗，**When** 按「登出」，**Then** 回到同一頁的「老師登入」，網址維持 `/teacher`，
   此視窗不再收到任何活動的即時更新。

### User Story 3 - 老師在單一頁面完成一整場活動 (Priority: P1)

老師在 `/teacher` 一頁內完成一整場活動：匯入並確認學習單、建立活動、開始、監看作答、判定無效、結束，最後寫回答案並下載 CSV。
全程不需要切換頁面、重新整理，也不需要手動輸入學習單 ID 或活動 ID。

**Why this priority**: 這是老師使用系統的主要流程。目前要在兩個頁面之間切換，寫回時還要手動輸入兩個 ID，容易出錯。
2026-11-27 的完整驗證中，就實際發生過選錯名稱相近的學習單。

**Independent Test**: 1 個老師視窗加上 2 個學生視窗跑完一場活動，確認老師全程停留在 `/teacher`，並且沒有手動輸入任何 ID。

**Acceptance Scenarios**:

1. **Given** 已登入的老師，**When** 匯入並確認一份學習單，**Then** 不必重新整理，「已確認的學習單」清單與「建立搶答活動」的學習單選單
   都立即出現這份學習單。（E-05）
2. **Given** 已確認的學習單，**When** 老師建立活動、開始、讓學生送出、判定無效、結束，**Then** 「目前活動」區塊依序呈現各階段，
   並保有既有主控台的所有功能（組別代碼、成功題數、冷卻、重新產生代碼、作答狀況、判定無效）。
3. **Given** 剛結束的活動，**When** 老師查看「目前活動」區塊，**Then** 出現「寫回答案」與「下載 CSV」兩個按鈕；
   按下後直接處理這場活動與它所用的學習單，不需要輸入任何 ID。（E-06）
4. **Given** 寫回完成，**When** 結果回傳，**Then** 顯示已填、未填，以及因格子已有內容而跳過的題號；寫回失敗時顯示既有的錯誤訊息
   （例如 Google 授權失效、學習單結構改變、沒有編輯權限）。
5. **Given** 下載 CSV，**When** 下載完成，**Then** 顯示紀錄筆數；若這場活動沒有任何送出，顯示「此活動沒有任何送出紀錄」。
6. **Given** 活動還在準備中或搶答中，**When** 老師查看「目前活動」區塊，**Then** 不顯示「寫回答案」與「下載 CSV」。

### User Story 4 - 老師從活動清單檢視過去的活動 (Priority: P2)

老師在「活動清單」看到所有活動。按某一場的「檢視」後，那場活動顯示在「目前活動」區塊；如果已結束，就能在那裡寫回或下載 CSV。
這一區取代原本「寫回答案與匯出結果」裡的活動選單與 ID 輸入框。

**Why this priority**: 老師常在課後才寫回，或需要重新下載 CSV；伺服器重新啟動後，也要能找到之前已結束的活動。
不過一般流程中，活動結束後直接在「目前活動」寫回即可（US3），所以優先度次之。

**Independent Test**: 先完成兩場活動，再從清單分別檢視，確認顯示的內容、寫回與下載都對應到正確的那一場。

**Acceptance Scenarios**:

1. **Given** 老師有多場活動，**When** 查看「活動清單」，**Then** 每列顯示編號、學習單名稱、階段、建立時間、結束時間，以及「檢視」按鈕。
2. **Given** 一場已結束的活動，**When** 按它的「檢視」，**Then** 該活動顯示在「目前活動」區塊，可以寫回或下載 CSV。（E-07）
3. **Given** 一場已中斷的活動，**When** 按它的「檢視」，**Then** 顯示這場活動已中斷、沒有結果可以檢視的說明，「目前活動」區塊維持原本內容。
4. **Given** 老師建立或結束一場活動，**When** 操作完成，**Then** 「活動清單」自動更新，不必重新整理頁面。

---

### User Story 5 - 舊網址自動導向新網址 (Priority: P3)

有人照著舊的說明或書籤開啟舊頁面網址時，系統自動帶到對應的新頁面，不會看到舊畫面或找不到頁面。

**Why this priority**: 只影響習慣舊網址的少數人，但可以避免 Demo 或上課時出現找不到頁面的錯誤。

**Independent Test**: 分別開啟兩個舊網址，確認被帶到的新網址與畫面。

**Acceptance Scenarios**:

1. **Given** 任何人，**When** 開啟 `/student.html`，**Then** 被帶到首頁 `/`，看到「加入組別」。（E-10）
2. **Given** 任何人，**When** 開啟 `/teacher.html`，**Then** 被帶到 `/teacher`。（E-10）

---

### Edge Cases

- **同一瀏覽器的多個視窗**：視窗 1 在 `/teacher` 登入，視窗 2、3 在首頁分別加入第一組、第二組，然後各自重新整理：三個視窗都維持原本的身分與畫面，互不影響。（E-08）
- **已登入老師的視窗開啟首頁**：仍顯示學生的「加入組別」，不會自動變成學生，也不會帶入老師身分；按「我是老師」回到 `/teacher` 時，仍是已登入狀態。
- **學生視窗保有的身分已失效**：例如伺服器重啟後重新整理，回到「加入組別」並顯示既有的提示訊息，不會停在空白或錯誤的作答畫面。
- **老師登入已失效**：例如老師權杖過期，或伺服器重啟後重新整理 `/teacher`，顯示登入畫面，不顯示任何活動資料。
- **沒有任何活動時**：「目前活動」區塊顯示目前沒有活動的說明，「活動清單」為空。
- **沒有已確認的學習單時**：「已確認的學習單」清單為空，建立活動的學習單選單沒有可選項目，並提示先匯入學習單。
- **匯入後按「取消」**：這份學習單不會出現在已確認清單與建立活動的選單中。
- **已有進行中的活動時建立新活動**：顯示既有的錯誤訊息（同一時間只能有一場進行中的活動），「目前活動」維持原活動。
- **寫回同一場活動兩次**：沿用 001 的規則，已寫入的格子不會被覆蓋；第二次寫回時，這些題號列為跳過。
- **活動已結束但寫回失敗**：顯示錯誤訊息後，按鈕仍可使用，老師處理好原因後可以再按一次。

## Requirements *(mandatory)*

### Functional Requirements

**學生頁（首頁 `/`）**

- **FR-001**: 首頁 MUST 為學生頁。未加入組別時，MUST 顯示「加入組別」標題、說明文字（每個瀏覽器視窗各自保有自己的身分，可以在不同視窗分別開啟老師與各組畫面）、
  組別代碼欄位，以及並排的「加入」「我是老師」兩個按鈕；MUST NOT 顯示老師密碼欄或任何老師功能。
- **FR-002**: 「我是老師」MUST 帶使用者到老師頁 `/teacher`。
- **FR-003**: 加入成功後，系統 MUST 在同一頁顯示原學生頁的全部內容：組名、目前階段、冷卻、作答區、結束後的結果與各組成功題數；
  網址 MUST 維持首頁，「加入組別」區塊與「我是老師」按鈕 MUST 隱藏。
- **FR-004**: 加入失敗時（代碼錯誤、格式不正確、輸錯次數達上限、沒有可加入的活動），MUST 留在「加入組別」，並顯示既有的錯誤訊息。
- **FR-005**: 學生身分失效時（代碼被重新產生、活動已中斷、身分無效），MUST 回到「加入組別」，並顯示既有的提示訊息。
- **FR-006**: 重新整理首頁時，若此視窗保有學生身分，系統 MUST 先確認身分是否仍有效：有效就直接顯示作答畫面，無效就顯示「加入組別」。

**老師頁（`/teacher`）**

- **FR-007**: 系統 MUST 在 `/teacher`（網址不含副檔名）提供老師頁。未登入時，MUST 只顯示「老師登入」區塊（密碼欄與「登入」按鈕）。
- **FR-008**: 登入後，頁首 MUST 只保留「登出」按鈕；畫面上 MUST NOT 出現切換到其他網頁的連結。
- **FR-009**: 登入後，MUST 在同一頁由上而下依序顯示五個區塊：匯入學習單、已確認的學習單、建立搶答活動、目前活動、活動清單。
- **FR-010**: 「匯入學習單」區塊 MUST 保有既有的試算表網址輸入、預覽、確認、取消功能，以及既有的錯誤訊息。
- **FR-011**: 「已確認的學習單」區塊 MUST 列出老師所有已確認的學習單，每筆顯示編號、試算表名稱、題數、題組數、確認時間。
- **FR-012**: 學習單確認後，「已確認的學習單」清單與「建立搶答活動」的學習單選單 MUST 立即更新，不需要重新整理頁面。
- **FR-013**: 「建立搶答活動」區塊 MUST 保有既有的欄位與驗證：學習單選單、組名（每行一組）、是否啟用公平機制、冷卻秒數 N、領先門檻 K。
- **FR-014**: 「目前活動」區塊 MUST 保有既有主控台的全部功能：顯示階段、開始搶答、結束搶答；組別表（組名、組別代碼、成功題數、冷卻、重新產生代碼）；
  作答狀況與判定無效（含確認步驟）。沒有活動時，MUST 顯示目前沒有活動的說明。
- **FR-015**: 「目前活動」為已結束的活動時，MUST 顯示「寫回答案」與「下載 CSV」兩個按鈕，直接處理這場活動與它所用的學習單，
  MUST NOT 要求輸入學習單 ID 或活動 ID。活動未結束時，MUST NOT 顯示這兩個按鈕。
- **FR-016**: 寫回後，MUST 顯示已填、未填，以及因格子已有內容而跳過的題號；寫回失敗時，MUST 顯示既有的錯誤訊息，並保留重試的能力。
- **FR-017**: 下載 CSV 後，MUST 顯示紀錄筆數；紀錄為 0 筆時，MUST 改為顯示「此活動沒有任何送出紀錄」。
- **FR-018**: 「活動清單」MUST 列出老師的所有活動，每列顯示編號、學習單名稱、階段、建立時間、結束時間，以及「檢視」按鈕。
  建立或結束活動後，清單 MUST 自動更新。
- **FR-019**: 按「檢視」後，MUST 把該活動顯示在「目前活動」區塊；已結束的活動 MUST 能在那裡寫回或下載 CSV。
  若活動已中斷，MUST 顯示「這場活動已中斷，沒有結果可以檢視」之類的說明，「目前活動」區塊維持原本內容。
- **FR-020**: 「活動清單」與「目前活動」的寫回、下載功能 MUST 完全取代原本的「寫回答案與匯出結果」區塊（已結束活動選單、學習單 ID、活動 ID 輸入框）。
- **FR-021**: 按「登出」後，MUST 回到同一頁的「老師登入」區塊，網址維持 `/teacher`，並停止此視窗的即時更新。
- **FR-022**: 重新整理 `/teacher` 時，若此視窗保有老師身分，系統 MUST 先確認身分是否仍有效：有效就直接顯示登入後的畫面，無效就顯示登入畫面。

**共通**

- **FR-023**: 即時更新連線 MUST 只在老師登入或學生加入之後才建立；未登入、未加入的畫面 MUST NOT 建立連線。
- **FR-024**: 同一瀏覽器的每個視窗 MUST 各自保有身分（老師或某一組），重新整理後維持不變，視窗之間互不影響（Constitution「專案範圍與限制」）。
- **FR-025**: 開啟 `/student.html` 時，MUST 被帶到首頁 `/`；開啟 `/teacher.html` 時，MUST 被帶到 `/teacher`。都 MUST NOT 顯示舊畫面或找不到頁面。
- **FR-026**: 學生頁 MUST 只包含學生需要的功能，老師頁 MUST 只包含老師需要的功能。
- **FR-027**: 本功能 MUST NOT 改變伺服器端的行為：
  - 既有功能 MUST 維持原樣，包括加入、登入、匯入、建立、開始、結束、送出、判定無效、寫回、匯出、即時更新的內容、權限檢查與資料保存。
  - 伺服器端只允許三項變更：新增老師頁的網址；改變首頁顯示的內容；在學習單清單資料中多回傳「確認時間」。
    第三項只新增欄位，不改變既有欄位與行為，用來滿足 FR-011。
- **FR-028**: 所有畫面文字與訊息 MUST 使用繁體中文，並沿用既有的訊息內容（Constitution 原則 II）。
- **FR-029**: 說明文件與設計文件中，所有提到舊頁面（`student.html`、`teacher.html`、「搶答主控台」「學習單與結果」）或舊進入方式的地方 MUST 同步更新為新的進入方式。範圍包括：
  - README 的操作說明
  - 001 的規格
  - 002 的計畫、任務與驗證紀錄
  - 畫有前端頁面的圖表

### Key Entities

本功能不新增或改變任何資料，只重新安排畫面。畫面上會用到下列既有資料：

- **視窗身分**：每個瀏覽器視窗各自保有的身分，只會是以下其中一種：未登入、老師、某一組學生。重新整理後保留，各視窗互不共用。
- **學習單**（001）：老師頁的「已確認的學習單」清單與建立活動選單會用到，包括編號、試算表名稱、題數、題組數、狀態、確認時間。
- **搶答活動**（002）：老師頁的「目前活動」與「活動清單」會用到，包括編號、所用的學習單、階段、建立時間、結束時間。
  寫回與下載 CSV 時，直接使用這場活動所用的學習單。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 學生從開啟首頁到看到作答畫面，只需要「輸入代碼、按加入」兩個動作，不需要輸入或修改任何網址。
- **SC-002**: 老師從首頁到看到登入後的畫面，只需要「按我是老師、輸入密碼、按登入」三個動作。
- **SC-003**: 老師跑完一整場活動（匯入 → 確認 → 建立 → 開始 → 結束 → 寫回 → 下載 CSV），全程停留在同一頁，重新整理 0 次、手動輸入 ID 0 次。
- **SC-004**: 同一瀏覽器的 1 個老師視窗加 2 個學生視窗，各自重新整理後，3 個視窗都維持原本的身分與畫面（3/3）。
- **SC-005**: 驗收情境 E-01～E-10 全部通過人工驗證；既有的自動化測試全部通過，代表伺服器端行為沒有改變。
- **SC-006**: 兩個舊網址都被帶到對應的新網址（2/2），不出現找不到頁面或舊畫面。
- **SC-007**: 兩組在課堂 Demo 時進入系統的方式一致：學生從首頁加入，老師從「我是老師」進入老師頁。

## Assumptions

- 以 OpenSpec 組交接文件為準：SpecKit 組完全對齊，OpenSpec 組不修改。交接文件中的版面順序、按鈕名稱與提示文字照原文採用。
- 本功能只調整頁面，所有業務規則、錯誤訊息與資料都沿用 001、002。伺服器端只有以下變更：
  - 提供 `/teacher` 頁面，並讓首頁顯示學生頁。
  - 學習單清單資料多回傳「確認時間」。交接文件要求在「已確認的學習單」顯示確認時間，但目前的清單資料只有匯入時間；
    系統其實已經保存確認時間，只是沒有提供給畫面。
    所以這項變更只是新增一個唯讀欄位，與交接文件「後端不用動」的原意（不改變行為）一致。
- 交接文件沒有說明「檢視已中斷的活動」時該怎麼呈現。因為已中斷的活動沒有保存任何結果，所以採用的做法是：顯示說明，並維持「目前活動」原本的內容。
- 交接文件沒有說明 CSV 為 0 筆時是否仍然下載。採用的做法是：仍下載只有表頭的檔案，畫面再顯示「此活動沒有任何送出紀錄」。
- 「活動清單」的「學習單」欄顯示學習單名稱（試算表名稱），方便辨認名稱相近的學習單。
- 老師登入後，「目前活動」預設顯示這次伺服器啟動後最近建立的活動，與現行主控台相同；伺服器重啟後若沒有新活動，就顯示目前沒有活動。
- 不使用新的前端框架或套件，沿用現有的頁面寫法。
- 系統仍只在單一電腦上，以多個瀏覽器視窗分別模擬老師與各組（Constitution「專案範圍與限制」）。
