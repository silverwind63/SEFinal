# Research: 線上分組搶答活動

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-11-22

本功能與 001 共用同一個程式套件 `guided_buzz`，以及 001 research 中的技術選擇：
Python 3.12 與 uv、FastAPI、SQLite、pytest、老師密碼登入、`GB_*` 設定，以及以 sessionStorage 存放 Token。
以下只記錄 002 新增的決策。

---

## R1. 判定順序與並行控制

- **Decision**: 伺服器只執行**單一程序**（uvicorn workers=1）。每場活動由一個存在記憶體中的 `ActivityEngine` 管理；
  所有會改變狀態的操作（開始、送出、判定無效、結束、重新產生代碼）都在同一把 `asyncio.Lock` 內依序執行。
  「伺服器處理順序」就是取得這把鎖的順序。
- **Rationale**: 一次只有一個操作能改變狀態，所以「恰好一個成功組別、順位不重複也不遺漏」（FR-012）自然成立，
  而且容易測試與推理。在單一電腦、13 個視窗的規模下，一次一個操作的吞吐量遠高於需求。
  鎖內不做任何網路等待；推播在鎖釋放後才進行，所以慢速的連線不會拖慢判定。
- **Alternatives considered**: 用資料庫交易與唯一索引決定成功者（每次送出都要寫入磁碟，與 Clarification
  「進行中的活動不保存」的決定不一致，也比較慢）；使用多程序（記憶體狀態無法共用）。
- **限制**: 啟動程式 MUST 固定 workers=1，並在 README 說明原因。

## R2. 即時同步

- **Decision**: 每個瀏覽器視窗建立一條 WebSocket（`/ws`）。連線後的第一則訊息才送出 Token 進行驗證，
  Token 不放在網址上，避免出現在存取紀錄裡。伺服器依連線的身分（老師，或某一組）**分別產生**要推送的內容：
  學生只會收到自己組別的資料，以及全體共用的階段訊息。
- **Rationale**: 2 秒內同步（SC-001）在本機輕易達成。依身分產生內容，代表「學生看不到他組資料」由伺服器保證（FR-014），
  不是由前端過濾。每次連線（含重新連線）都會先收到一份完整的目前狀態，之後才收到增量事件，
  所以不需要補送斷線期間漏掉的事件（FR-003）。
- **Alternatives considered**: 每秒輪詢（延遲與負擔較高，程式也比較繁雜）；Server-Sent Events
  （只能由伺服器單向傳送，而且自動重連需要另外處理身分）。

## R3. 學生身分：組別代碼與每個視窗的獨立身分

- **Decision**:
  - **組別代碼**：以 `secrets` 從去除易混淆字元的 31 個字元中隨機產生 6 碼；同一場活動內不重複。
    明文只存在記憶體中，供老師畫面顯示；資料庫只存 SHA-256 雜湊。
  - **加入組別**：`POST /api/join` 送出代碼，換到一個學生 Token。Token 記錄所屬的活動、組別與代碼版本，
    前端存在 sessionStorage，所以每個視窗各自獨立（FR-005a）。
  - **重新產生代碼**：代碼版本加 1，舊代碼與用舊代碼取得的 Token 立即失效，對應的 WebSocket 連線也會被關閉（FR-005b）。
  - **輸錯限制**：前端在每個視窗第一次載入時產生一個隨機的視窗 ID，存在 sessionStorage，之後的請求都以
    `X-Window-Id` 標頭送出。輸錯次數以視窗 ID 計算，連續錯誤 `GB_JOIN_MAX_FAILURES` 次（預設 5 次）後，
    鎖定 `GB_JOIN_LOCK_SECONDS` 秒（預設 60 秒）。另設全體輸錯上限（預設每分鐘 60 次），
    超過時所有新的加入請求都要延遲，以防有人不斷換新的視窗 ID 來規避限制。
- **Rationale**: 所有視窗都來自同一個 IP，用 IP 鎖定會封鎖全班（規格邊界案例）。視窗 ID 可以由使用者偽造，
  所以再加上全體上限，在課堂情境下足以防止猜碼：6 碼代碼共約 8.9 億種組合。
- **Alternatives considered**: 用 Cookie 存身分（同一瀏覽器的各視窗會共用）；用 IP 限制輸錯次數（會封鎖全班）。

## R4. 搶答單位的表示方式

- **Decision**: 依 001 的 `ParsedWorksheet` 建立搶答單位：每個題組是一個單位，鍵值為 `G<group_no>`；
  不屬於題組的題目各自是一個單位，鍵值為 `Q<question_no>`。單位依其中最小的題號排序。
  `BuzzUnit` 定義在共用的 `domain/models.py`。
- **畫面顯示**: 學生與老師都只看到題號標示，例如「第 5 題（學習單第 3 題）」或「題組 1：第 1、2 題（學習單第 1 題（1）（2））」，
  不顯示題目敘述。學生對照手上的學習單作答（這是 clarify 階段留下的小項目，在此決定）。

## R5. 送出處理規則（在鎖內依序檢查）

1. 活動階段必須是「搶答中」，否則回應 `NOT_RUNNING`（FR-006）。
2. Token 有效，且對應組別的代碼版本仍是目前版本，否則回應 `UNAUTHORIZED`。
3. 組別不在冷卻中，否則回應 `COOLDOWN`，並附剩餘秒數。這種送出**不記錄**、不佔順位，冷卻後可以再送（FR-019）。
4. 單位存在，否則回應 `UNKNOWN_UNIT`；答案的題號集合必須等於該單位的題號集合，否則回應 `INCOMPLETE_GROUP`，
   並列出缺少或多出的題號（FR-007）。
5. 每個答案去除前後空白後不可為空，且長度 ≤ `GB_MAX_ANSWER_LENGTH`（預設 200），否則回應 `INVALID_ANSWER`（FR-009）。
6. 這個組別對這個單位沒有送出過任何紀錄，否則回應 `ALREADY_SUBMITTED`（FR-008）。
7. 順位 = 這個單位現有紀錄數 + 1。如果這個單位目前沒有成功者（從未有人送出，或成功者被判無效後無人遞補），
   這次送出就是成功，否則是「未搶到」（FR-010、FR-011）。
8. 成功時檢查公平機制：若「這組成功數 − 所有組中的最少成功數 ≥ K」，這組冷卻 N 秒，
   冷卻紀錄會記下是哪一筆成功觸發的（FR-018）。
9. 回應送出結果（FR-013），並在鎖釋放後推播給同組的所有視窗與老師。

**時間**：冷卻倒數使用 `time.monotonic()`，不受系統時鐘調整影響；顯示與紀錄使用伺服器的 UTC 時間。
時鐘以注入方式提供，測試時可以換成假時鐘。

## R6. 判定無效與遞補

- **Decision**: 在鎖內進行。把成功的那筆送出標為 `invalidated`，再依順位找下一筆 `not_won`，把它升為 `success`。
  找不到時，這個單位回到「沒有成功者」的狀態：搶答中會重新開放，已結束則顯示「無人搶答」。
  如果被判無效的組正因這次成功而冷卻，冷卻立即解除；遞補成功不會觸發冷卻（FR-022～FR-024）。
  已結束的活動做判定無效時，以一筆資料庫交易同時更新兩筆送出的結果。
- **通知**: 被判無效的組收到「第 X 題的答案已被老師判定無效」；遞補成功的組收到「第 X 題遞補為搶答成功」，
  兩則通知都不包含他組的答案（FR-025）。

## R7. 保存與重啟（Clarification：只保存已結束的活動）

- **Decision**:
  - **建立活動時**：寫入 `activities`（狀態為準備中）與 `teams`（只存代碼雜湊）。
  - **開始搶答時**：把狀態更新為「搶答中」。進行中的送出只存在記憶體。
  - **結束搶答時**：在鎖內以一筆交易寫入所有送出與答案，並把狀態改為「已結束」。交易確認成功後，
    才把記憶體中的階段改為已結束並推播。寫入失敗時，維持搶答中並告知老師錯誤（FR-026）。
  - **伺服器啟動時**：把所有「準備中」與「搶答中」的活動改為「已中斷」（FR-027）。
  - **中斷後的提示**：前端在 sessionStorage 記住活動 ID，重新連線時呼叫公開的 `GET /api/activities/{id}/phase`，
    只回傳階段，不含任何資料；若為已中斷，就顯示「活動已中斷，請老師重新建立」。
- **Rationale**: 符合 Clarification 的選擇 B，同時讓學生與老師在重啟後得到清楚的說明，而不是只看到「Token 無效」。

## R8. 與 001 的介面

- **Decision**: 實作 001 定義的 `ActivityResultsProvider` 介面，命名為 `SqliteActivityResultsProvider`，
  從已結束的活動讀出 `ActivityResult`，裡面的 `SubmissionRecord.outcome` 使用 001 的列舉
  `success`、`not_won`、`invalidated`。002 完成後，001 的寫回與匯出改用這個實作。
- **共用資料結構**: 002 新增的 `BuzzUnit`、`ActivityPhase`、`SubmissionRejectCode` 都加到 `domain/models.py` 與
  `domain/errors.py`，不另建一份定義。

## R9. 同時只有一場活動

- **Decision**: 已有「準備中」或「搶答中」的活動時，建立新活動一律回應 409。
  同一份學習單可以先後舉辦多場活動；001 的寫回與匯出由老師選擇要用哪一場已結束的活動。

## R10. 新增的設定

| 變數 | 預設 | 說明 |
|------|------|------|
| `GB_MAX_TEAMS` | 20 | 組數上限 |
| `GB_TEAM_NAME_MAX` | 20 | 組名長度上限 |
| `GB_MAX_ANSWER_LENGTH` | 200 | 答案長度上限 |
| `GB_FAIRNESS_ENABLED` | true | 是否啟用公平機制 |
| `GB_COOLDOWN_SECONDS` | 10 | N |
| `GB_COOLDOWN_LEAD` | 2 | K |
| `GB_JOIN_MAX_FAILURES` / `GB_JOIN_LOCK_SECONDS` | 5 / 60 | 每個視窗的輸錯限制 |
| `GB_JOIN_GLOBAL_FAILURES_PER_MIN` | 60 | 全體輸錯上限 |

建立活動時，老師可以在畫面上覆寫 N、K 與是否啟用公平機制；沒有覆寫時使用上表的預設值。
覆寫後的值保存在 activities 資料表中。

## R11. 測試策略

- **判定引擎單元測試**：直接呼叫 `ActivityEngine`，搭配假時鐘，以 `asyncio.gather` 讓多組同時送出，重複 100 次（SC-002）；
  另外測試冷卻、判定無效與遞補、題組送出的各種邊界情況。
- **API 與 WebSocket 整合測試**：使用 FastAPI TestClient，涵蓋學生取得他組資料一律被拒（SC-003）、
  不同視窗的身分彼此獨立、重新連線先收到完整狀態等情況。
- **公平機制模擬**：用固定的亂數種子模擬「一組反應最快」的情境，比較啟用與停用公平機制時，
  至少成功一題的組數（SC-006）。
- **重啟測試**：建立兩個不同的 app 實例，共用同一個資料庫檔案，驗證已結束的結果完整保留、未結束的活動變成已中斷。
